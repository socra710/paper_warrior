# 종이전사 버전 관리 정책 (VERSION POLICY)

## 1. 기본 정책

Semantic Versioning(SemVer)의 `MAJOR.MINOR.PATCH` 형식을 사용한다. 예: `0.3.1`.
작업 완료 자체는 버전 증가 사유가 아니다. 변경 성격과 배포 필요성을 판단하며, 개발 중에는 정식 출시 전까지 MAJOR를 `0`으로 유지하는 것이 기본이다.

게임 버전의 단일 기준은 `project.godot`의 `application/config/version`이다. 화면·웹 셸의 표시는 이 값을 사용한다. Git 릴리스 태그는 `v` 접두사를 붙인다.

## 2. 증가 기준

| 유형 | 기준 | 대표 사례 |
|---|---|---|
| MAJOR | 기존 버전과 호환되지 않는 대규모 변경 | 저장 데이터 구조 비호환, 핵심 시스템 전면 변경, 설정·진행 데이터 호환 중단, 정식 출시 `1.0.0` |
| MINOR | 호환성을 유지하며 새로운 기능·콘텐츠 추가 | 신규 게임·성장 시스템, 장비·아이템, 몬스터·스테이지, 화면·메뉴, 대규모 플레이 기능 |
| PATCH | 기존 기능의 오류 수정·소규모 품질 개선 | 버그, UI 배치, 캐릭터 그래픽·애니메이션 보완, 성능·로딩, 사운드, 문구, 기존 세부 동작 개선 |

MINOR 증가 시 PATCH는 `0`으로 초기화한다(`0.3.2 → 0.4.0`). PATCH 증가 시 MAJOR와 MINOR는 유지한다(`0.3.0 → 0.3.1 → 0.3.2`).

여러 작업을 묶으면 가장 높은 변경 수준을 적용한다: **MAJOR > MINOR > PATCH**.

- 버그 수정만 포함: PATCH.
- 신규 장비 + 버그 수정, 신규 성장 시스템 + UI 개선: MINOR.
- 호환성을 깨는 시스템 변경 + 신규 기능: MAJOR.

기준이 불명확하거나 MAJOR 변경이 필요하면 에이전트가 임의로 결정하지 않고 사용자에게 먼저 확인한다. 출시 전 `0.x`라는 이유로 비호환 변경의 영향 보고를 생략하지 않는다.

## 3. 이해를 위한 예시

| 버전 | 예시 변경 |
|---|---|
| `0.1.0` | 초기 개발 버전 |
| `0.2.0` | 신규 기능 |
| `0.3.0` | 신규 게임 시스템 |
| `0.3.1` | 캐릭터 애니메이션 오류 수정 |
| `0.3.2` | UI·화면 배치 개선 |
| `0.3.3` | 전투 성능 개선 |
| `0.4.0` | 신규 콘텐츠 |
| `0.4.1` | 신규 콘텐츠 버그 수정 |
| `0.5.0` | 신규 성장 시스템 |
| `1.0.0` | 정식 출시 |

이 표는 정책 예시이며 실제 구현 이력이나 확정된 로드맵이 아니다.

## 4. Copilot Agent 필수 절차

1. 작업 시작 전 현재 프로젝트 버전과 공개 배포 버전을 확인한다.
2. 변경하려는 작업의 성격과 PATCH / MINOR / MAJOR 유형을 분석한다.
3. 버전 증가가 실제로 필요한지 판단한다. 하나의 업데이트로 묶는 작업은 종합해서 결정한다.
4. 작업 중 임의로 버전을 여러 번 증가시키지 않는다.
5. **사용자 승인 없이 정식 릴리스 버전을 확정하거나 배포하지 않는다.** 기존의 일반적인 배포 요청을 새 버전에 대한 승인으로 간주하지 않는다. 제안·검증·승인·게시를 구분한다.
6. 실제로 구현하지 않은 기능을 릴리스 내역에 기록하지 않는다.
7. 버전 변경 시 프로젝트, 게임 화면, 웹 셸, 빌드 manifest, 배포 `version.json`, Git 태그, ZIP 파일명과 CHANGELOG의 참조가 일치하는지 확인한다. 이전 이력과 정책 예시의 버전을 새 번호로 일괄 치환하지 않는다.
8. 저장 데이터 호환성에 영향을 주면 별도로 보고한다.

## 5. CHANGELOG 기록

모든 정식 업데이트는 저장소 루트의 [`CHANGELOG.md`](../CHANGELOG.md)에 기록한다.

- 개발 중인 변경은 `[Unreleased]`에 기록하고 정식 업데이트 완료로 표시하지 않는다.
- 사용자 승인과 실제 게시가 끝나면 버전, 실제 업데이트 날짜(`YYYY-MM-DD`), 업데이트 유형과 다음 분류를 기록한다.
- `Added`: 신규 기능.
- `Changed`: 기능 변경.
- `Fixed`: 버그 수정.
- `Improved`: 성능·품질 개선.
- `Migration`: 데이터·호환성 변경.
- 해당 분류의 변경이 없으면 `없음`으로 명시한다. 테스트하지 않은 결과나 미구현 기능을 완료 항목으로 넣지 않는다.

기록 형식:

```markdown
## [승인된 버전] - 실제 게시 날짜

업데이트 유형: PATCH / MINOR / MAJOR 중 해당 유형

### Added
- 실제 신규 기능 또는 없음.

### Changed
- 실제 변경 또는 없음.

### Fixed
- 실제 수정 또는 없음.

### Improved
- 실제 개선 또는 없음.

### Migration
- 저장 데이터·설정 호환성 영향 또는 없음.
```

## 6. 릴리스·배포

- 개발은 작업 브랜치에서 진행한다. 현재 사용자 지정 브랜치는 `socra710`이다.
- 하나의 릴리스에는 검증된 변경만 포함한다.
- 승인받은 버전으로 한 번 빌드하고 빌드 버전과 실제 배포 버전을 일치시킨다.
- 소스는 `socra710/paper_warrior`, 랜딩·Web·Windows 배포는 `socra710/paper_warrior_releases`에서 관리한다.
- 게시 후 실제 브라우저에서 배포 버전과 새 파일 반영 여부를 확인한다.
- 배포 미완료 또는 확인 실패 상태를 정식 업데이트 완료로 기록하지 않는다.
- 이전 릴리스로 복구할 수 있도록 Git 태그를 보존하고 새 정식 릴리스에는 `v0.3.1` 같은 태그를 생성한다. 이미 게시한 태그·버전을 덮어쓰지 않는다.

## 8. 품질 복구 당시의 판단 기록

- 당시 프로젝트·공개 버전: `0.3.0`.
- 제안: `0.3.1` / **PATCH**. 기존 시작 화면 구분, 로딩 오류·진행 표시, 캐릭터 외형·애니메이션 품질 복구이며 신규 게임 시스템·콘텐츠가 아니다.
- 신규 게임 기능, 저장 데이터·설정 형식 변경은 없다.
- 당시 조사 폴더 `quality-v040`와 복구 태그 `quality-before-v0.4.0`은 정책 도입 전의 작업 식별자이며 그 자체가 배포 승인을 의미하지 않는다.
- 이후 신규 메뉴 진입점을 함께 묶어 0.4.0/MINOR를 제안했고, 사용자 승인과 공개 검증 후 2026-11-12에 사전 릴리스를 게시했다.
