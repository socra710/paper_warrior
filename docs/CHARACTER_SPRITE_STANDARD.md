# 종이전사 캐릭터 스프라이트 제작 지침

## 적용 원칙

종이전사는 픽셀 아트 기반 게임이다. 기존 전사의 색상, 얼굴과 신체 비율, 접힌 면, 작은 검과 별 방패를 유지한다. 애니메이션별로 캐릭터를 새로 해석하지 않는다. 기존 구현과 연결된 씬/스크립트를 조사한 뒤 교체하며, 구현하지 않은 애니메이션이나 게임 기능을 완료로 표시하지 않는다.

## 원본과 실행 에셋

- **SVG 마스터:** 수정 가능한 원본으로 보관한다. 초기 캐릭터 프로토타입, 동작 검증, UI 아이콘/장식, 간단한 이펙트, 개발 중 임시 그래픽에 사용할 수 있다.
- **최종 캐릭터 기본 형식:** 투명 배경 RGBA PNG 스프라이트 시트다. SVG 마스터를 분석·검증하고 픽셀 크기 그대로 래스터화한다.
- SVG를 Godot 텍스처로 직접 가져와 검증할 수 있지만 최종 캐릭터는 PNG를 우선한다. 두 형식의 실제 게임 내 품질을 비교한 뒤 성능·시각 품질·유지보수성을 기준으로 결정한다.
- Godot는 SVG도 import 시 텍스처로 변환한다. 따라서 SVG가 매 프레임 벡터를 다시 그린다고 가정하거나 PNG 전환만으로 성능이 개선됐다고 보고하지 않는다. PNG는 최종 픽셀과 알파, 프레임 규격을 명확히 관리하기 위해 선택한다.

## 시트 규격

| 항목 | 기준 |
|---|---|
| 기본 프레임 | 48×48px |
| 배치 | 가로 방향, 프레임 간 간격 없음 |
| 배경 | 완전 투명 |
| 중심/기준선 | 프레임 중심 (24,24), 발 기준선 y=44를 모든 프레임에서 유지 |
| 신체 연결점 | 머리·몸통·어깨·골반·장비의 연결점과 회전 기준점을 고정 |
| 일관성 | 머리·얼굴·몸통의 크기와 비율, 색, 외형, 접지 기준선을 유지 |

대기와 걷기를 한 파일에 보관해도 SpriteFrames의 애니메이션 이름과 프레임 영역은 독립적으로 관리한다. 공격·피격·사망·승리도 별도 애니메이션으로 관리하며 걷기 프레임을 재사용해 완료된 것처럼 표기하지 않는다.

## SVG 구조

`defs`에 머리, 얼굴, 몸통, 좌우 팔, 다리, 검, 방패 등을 이름 있는 공통 부품으로 선언하고 `use`로 재사용한다. 프레임마다 같은 신체 부품을 복제하지 않는다. 신체 부위별 그룹을 유지하고 공통 팔레트로 색상을 관리한다.

회전이 필요하면 고정된 연결점/기준점을 사용한다. 단순 회전 반복이 아니라 발의 접지, 골반/몸통의 이동, 팔과 장비의 반동을 조합해 무게중심 이동을 표현한다. 접힌 면과 종이 겹침을 동작 중에도 보존한다.

### 공통 부품 + 애니메이션 데이터

프레임마다 SVG 코드를 처음부터 작성하지 않는다. **공통 외형**과 **애니메이션별 위치·변형 정보**를 분리한다.

| 원본/도구 | 책임 |
|---|---|
| `assets/characters/warrior/warrior_parts.svg` | 공통 팔레트, 머리·얼굴·몸통·좌우 팔·다리·검·방패의 단일 마스터 |
| `data/presentation/warrior_animation.json` | 프레임 크기, 기준점/기준선, 부품 순서와 Idle/Walk의 프레임별 위치·변형 |
| `scripts/art/build_warrior_sprites.gd` | 공통 부품과 동작 데이터를 결합해 SVG/PNG 시트와 SpriteFrames 씬 생성 |
| `warrior_idle_walk.svg`, `warrior_idle_walk.png`, `scenes/characters/warrior_sprite.tscn` | 재생성 가능한 산출물. 외형이나 동작을 여기서 개별 수정하지 않음 |

기하 도형은 SVG 마스터에만 두고 JSON에 복제하지 않는다. 프레임 데이터는 공통 부품을 참조하는 변형만 보관한다. 얼굴, 접힌 면, 검이나 방패를 개선할 때 공통 마스터 한 곳을 수정하고 전체 애니메이션을 재생성하여 같은 외형을 적용한다.

현재 Idle/Walk 생성기는 부품별 정수 이동을 사용한다. 회전/스케일 변형을 추가할 때는 고정된 관절 기준점을 사용하도록 동작 데이터와 생성기 검증을 함께 확장한다. 아직 지원하지 않는 변형을 데이터에 적는 것만으로 적용됐다고 판단하지 않는다.

```powershell
godot --headless --path . --script res://scripts/art/build_warrior_sprites.gd
godot --headless --editor --path . --import
```

재생성 후 픽셀/알파, 모든 프레임, SpriteFrames 연결과 실제 게임 재생을 다시 검증한다. 공격 등 새 동작을 추가할 때도 공통 외형은 복사하지 않고 해당 애니메이션의 동작 데이터만 추가한다.

## 픽셀 품질과 팔레트

정수 좌표와 픽셀 경계에 맞춘 도형을 우선하고 불필요한 안티앨리어싱을 방지한다. 외곽선은 같은 짙은 청색 잉크와 일관된 두께를 사용한다. 색상 단계는 제한하며 접힘, 겹침, 명암과 그림자로 종이의 두께를 표현한다. 단순한 평면 도형으로 대체하지 않는다.

기본 색상은 크림 `#f7f4e9`, 민트 `#cce4d8`, 하늘색 `#d3e6ee`, 노랑 `#f2cd7e`, 잉크 `#2d495b`와 기존 아트 가이드의 제한된 명암색이다. 모든 프레임에 같은 팔레트를 적용한다.

## 애니메이션 표준

| 애니메이션 | 프레임 수 | 제작 기준 | 현재 범위 |
|---|---:|---|---|
| Idle | 4 | 호흡/시선과 미세한 무게 이동, 자연스러운 반복 | 시작 화면 및 맵 연출 |
| Walk | 6 | 교차 보행과 접지/이동 구분, 상하 움직임과 장비 반동 | 맵 둘러보기 연출 |
| Attack | 5~6 | 준비 → 타격 → 회복이 연결되는 독립 동작 | 미구현 |
| Hit | 2~3 | 피격 반응 → 자세 회복 | 미구현 |
| Death | 4~6 | 중심 상실 → 쓰러짐 → 종료 자세 | 미구현 |
| Victory | 4~6 | 시작 → 기쁨 표현 → 안정된 종료/복귀 | 미구현 |

걷기는 좌우 다리를 교차하고 지면에 남는 발과 이동하는 발을 구분한다. 몸통은 자연스럽게 오르내리고 팔·검·방패가 보행에 맞춰 움직여야 한다. 검과 방패를 몸통에 붙인 채 통째로 흔들지 않는다. 마지막 프레임에서 첫 프레임으로 접지와 무게 이동이 자연스럽게 이어져야 한다.

## Godot 연결

`AnimatedSprite2D`와 `SpriteFrames` 또는 동등한 독립 프레임 관리 시스템을 사용한다. AtlasTexture 영역은 정확히 48×48이고 텍스처 필터는 **Nearest**로 설정한다. 프레임 좌표와 기준점을 코드에서 임의로 보정해 흔들림을 가리지 않는다.

확대했을 때 픽셀이 흐려지지 않는지 확인한다. 브라우저 CSS 스케일과 기기 배율도 영향을 주므로 에디터 미리보기만으로 품질을 판정하지 않는다. 가능하면 정수 배율로 확대해 개별 프레임을 검사하고 실제 게임 크기에서도 다시 확인한다.

## 검증 및 완료 보고

1. 전체 시트의 크기, 투명 알파와 프레임 영역을 검사한다.
2. 개별 프레임을 확대해 외곽선, 접힌 면, 팔레트와 픽셀 경계를 확인한다.
3. Idle/Walk 등 각 애니메이션을 실제 재생해 연결과 접지, 무게중심, 장비 반동을 확인한다.
4. 프레임 간 위치 흔들림, 잘림, 외형 변화와 기준선 이동이 없는지 확인한다.
5. Godot에서 실제 크기와 확대 크기로 렌더링하고 SVG/PNG의 차이를 비교한다.
6. 웹에서 세로·가로 전환 후에도 필터, 프레임, 현재 화면과 상태가 유지되는지 확인한다.
7. 실제 실행한 검사와 결과, 미실행한 검사, 남은 품질 한계를 구분해 기록한다.

공격·피격·사망·승리 프레임 수는 제작 표준이며 현재 전투 기능이나 해당 에셋이 완성됐다는 뜻이 아니다.

### v0.3.0 실제 비교 결과

Godot 4.4.1에서 같은 480×48 SVG와 PNG를 Nearest 4배 및 실제 게임 크기로 비교했다. SVG import에는 부분 알파 15픽셀이 있었고 최종 PNG는 0픽셀이다. 생성기는 알파 임계 처리와 공통 팔레트 양자화로 RGBA PNG의 투명/불투명 경계와 7색을 고정한다. 10프레임 확대 시트, Idle 실제 재생, Walk 맵 이동과 가로/세로 화면을 확인했다.

외형은 SVG 마스터 한 곳에서 유지하고 PNG는 재생성하므로 외형 수정의 일관성을 유지한다. GPU/메모리/프레임 시간의 비교 벤치마크는 수행하지 않았으며 PNG가 더 빠르다고 주장하지 않는다.
